# One shared Supabase project across local dev, Preview, and Production

There is no separate dev database. Local dev, every Vercel Preview deploy, and Production all point at the same single Supabase project, reached through Supabase's **Shared Pooler** — transaction mode (`DATABASE_URL`, port 6543) for the running app, session mode (`MIGRATION_DATABASE_URL`, port 5432) for `drizzle-kit generate`/`migrate` — never the separate, paid-tier **Dedicated Pooler** (`docs/research.md` §4.3). Confirmed and fixed as the current, working state during a DB connection-URL diagnosis session (2026-09-04, issue #36/PR #37).

This is a deliberate free-tier stopgap, not an oversight: Supabase's free plan caps a team at 2 active projects and doesn't include **Branching** (Pro plan+), which is what would give each PR its own ephemeral, copy-on-write database. The two professional alternatives — a dedicated second Supabase project for dev/preview, or Branching for per-PR databases, either paired with migrations running from CI per environment rather than from a developer's machine — are known and deferred, not rejected. `scripts/supabase-setup.sh` already flags this out loud ("Preview and Production share this one Supabase project/database for now."). Practical consequence in the meantime: every `db:migrate` run, from any environment, touches the one real dataset — there's no dev/staging sandbox to make mistakes in safely.
